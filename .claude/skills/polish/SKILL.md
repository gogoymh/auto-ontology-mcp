# polish

에이전트가 쓴 글을 사람이 쓴 말처럼 고친다. 뜻, 수치, 코드 식별자, 파일 이름, 티켓 번호는 그대로 둔다. 바꾸는 것은 문장 모양뿐이다.

번호 패턴은 일곱 개다. 새 말버릇이 보여도 여덟 번째로 나누지 않고 아래 패턴에 넣는다.

## 쓰는 순서

1. 독자가 먼저 알아야 할 것(지금 상태, 달라진 것, 정할 것)을 첫 문장에 둔다.
2. 아래 패턴을 하나씩 찾아 고친다.
3. 다시 읽고 빼도 뜻이 통하는 말을 지운다.
4. 고치기 전과 뒤의 수치, 이름, 번호가 같은지 대조한다.

## 패턴 1. 번역투 (translationese)

영어 문장 구조를 옮긴 표현이다. 판단을 부풀리고 주어를 흐린다.

| 찾을 말 | 이렇게 |
| --- | --- |
| ~에 정확히 부합합니다, ~에 정확히 맞습니다 | ~입니다, ~라서 맡습니다 |
| ~을(를) 대상으로 ~을 수행합니다 | ~으로 ~합니다 |
| ~하도록 구현했습니다 | ~합니다, ~하게 했습니다 |
| ~ 통과를 확인했습니다 | ~를 통과합니다 |
| 이를 통해, 해당 ~ | 그래서, 이 ~ (또는 지운다) |
| ~가 아니라 ~입니다 (강조용) | 뒷말만 쓴다 |

고치기 전:
> 벤치마크 자동 실행·기준선 비교 연동은 @benchmark의 역할에 정확히 부합합니다.

고친 뒤:
> 벤치마크를 자동으로 돌려 기준선과 비교하는 일은 제 역할입니다.

고치기 전:
> 병합된 미션의 채점과 후속 티켓 정리는 제 역할에 정확히 맞고, 다른 봇이 맡은 일과도 겹치지 않습니다.

고친 뒤:
> 병합된 미션을 채점하고 후속 티켓을 정리하는 일은 제 몫이고, 다른 봇의 일과 겹치지 않습니다.

## 패턴 2. 파일명과 수치를 한 문장에 몰아 넣는 나열 (crammed list)

한 문장에 파일 경로, 괄호 설명, 개수, 점수가 다 들어가면 독자는 무엇이 달라졌는지 못 찾는다. 사용자가 얻는 동작을 먼저 한 문장으로 쓰고, 근거 수치는 다음 문장에, 파일 이름은 꼭 필요할 때만 마지막에 모은다. 괄호 안에 또 설명을 넣지 않는다. 괄호가 없어도 같다. 파일 경로가 셋 이상이고 수치와 저장하거나 추가하는 말(더했다, 만들었다, 고쳤다도 같다)이 한 문장에 있으면 나열이다. 숫자가 `test_v2.py`, `AOM-33`, `#28`처럼 파일 이름이나 번호 안에만 있으면 수치로 세지 않는다.

고치기 전:
> 내장 데모 DB와 지식 베이스를 대상으로 76개 고정 과제 셋(benchmarks/tasks.json)과 헤드리스 측정 및 비교 스크립트(benchmarks/run_benchmark.py)를 추가했습니다. 5개 핵심 영역 초기 기준선(benchmarks/baseline.json, 종합 점수 1.0000)을 저장했고 ruff 린트와 tests/test_benchmark.py 4개 테스트 통과를 확인했습니다.

고친 뒤:
> 내장 데모 DB와 지식 베이스로 돌리는 벤치마크를 더했습니다. 고정 과제 76개를 5개 영역에서 화면 없이 측정하고 비교하며, 첫 기준선은 종합 1.0000입니다. 과제는 `benchmarks/tasks.json`, 측정 스크립트는 `benchmarks/run_benchmark.py`, 기준선은 `benchmarks/baseline.json`에 있고, ruff와 `tests/test_benchmark.py`의 테스트 4개를 통과합니다.

고치기 전:
> pyproject.toml에 선택적 semantic extra(fastembed, sqlite-vec)를 추가하고, 설치된 환경에서 로컬 벡터 인덱스를 증분 갱신해 textindex.py(RRF 융합)와 search.py(점수 결합)의 하이브리드 검색을 수행하도록 구현했습니다.

고친 뒤:
> semantic extra를 설치하면 로컬 벡터 인덱스를 더한 하이브리드 검색을 씁니다. 설치하지 않으면 지금 검색이 그대로 동작합니다. extra는 fastembed와 sqlite-vec이고, 인덱스는 바뀐 부분만 다시 만듭니다. 결과는 `textindex.py`에서 RRF로, `search.py`에서 점수로 합칩니다.

## 패턴 3. 한국어 채널에 영어로 쓴 완료 보고 (English report in a Korean channel)

채널의 말이 한국어면 보고도 한국어로 쓴다. 코드 식별자, 명령, 지표 이름(recall@3, p50)은 원문 그대로 두고, 문장만 옮긴다. 제목과 첫 문장의 언어가 다르게 섞이지 않게 한다. 내용 없이 '작업을 마쳤습니다'만 남기지 말고 결과 한 문장을 붙인다.

고치기 전:
> Added 27 synonym, paraphrase and Korean-English cross-lingual queries to benchmarks/tasks.json. run_benchmark.py --semantic now compares lexical and hybrid search: recall@3 went from 0.40 to 0.84 (cross-lingual 0.00 → 0.83), and p50 latency went from about 4.9 ms to 9.3 ms.

고친 뒤:
> `run_benchmark.py --semantic`으로 어휘 검색과 하이브리드 검색을 비교합니다. 하이브리드 검색은 recall@3을 0.40에서 0.84로 올렸고, 한영 교차 질문은 0.00에서 0.83이 됐습니다. 대신 p50 지연은 약 4.9 ms에서 9.3 ms로 늘었습니다. 비교에 쓴 동의어, 바꿔 말하기, 한영 교차 질문 27개는 `benchmarks/tasks.json`에 더했습니다.

고치기 전:
> I reviewed both new PRs. #27 needs changes before it can merge, and #28's results are correct.

고친 뒤:
> 새 PR 두 개를 리뷰했습니다. #27은 병합 전에 고칠 곳이 있고, #28은 결과가 맞습니다.

## 패턴 4. '~한 상태에서 ~되었고'처럼 길게 이어지는 문장 (chained sentence)

'~한 상태에서', '~되었고', '~한 반면', '~하므로'로 사실 서너 개를 한 문장에 이으면 주어가 중간에 바뀌고 결론이 맨 끝에 묻힌다. 사실 하나에 한 문장을 쓰고, 결론(그래서 무엇을 하는지)을 앞이나 끝에 따로 둔다. 원인과 결과처럼 붙어 있어야 뜻이 사는 것만 한 문장으로 잇는다. `되어 있고`가 두 번 있는 것은 사실을 서너 개 잇는 문장이 아니다.

고치기 전:
> AOM-13으로 구축한 벤치마크 스크립트와 기준선이 preconquer-gogoymh에 병합된 상태에서 새 이슈 AOM-15(CI에 벤치마크 기준선 비교 단계 추가)가 미할당으로 등록되었고, 벤치마크 자동 실행·기준선 비교 연동은 @benchmark의 역할에 정확히 부합합니다.

고친 뒤:
> AOM-15를 맡습니다. AOM-13의 벤치마크 스크립트와 기준선은 preconquer-gogoymh에 병합됐고, CI에서 기준선과 비교하는 일(AOM-15)은 아직 맡은 사람이 없습니다. 이 일은 제 역할입니다.

고치기 전:
> 나머지 이슈는 원격 푸시·PR 관리·사용자 결정이 필요한 반면, 이 이슈는 코드만으로 독립 워크트리에서 구현·검증·병합할 수 있는 명확한 검색 품질 개선 작업입니다.

고친 뒤:
> 이 이슈는 코드만으로 워크트리에서 끝낼 수 있어 먼저 맡습니다. 나머지는 원격 푸시나 PR 관리, 사용자 결정을 기다려야 합니다.

## 패턴 5. 한자어 명사로 뭉친 조건과 시점 (noun stack)

'향후', '~ 시', '미설치', '미할당', '비활성화', '기존'처럼 한자어 명사로 조건과 시점을 접으면 문서 투가 되고, 무엇이 어떤 상태일 때인지 다시 풀어 읽어야 한다. 동사로 풀어 '앞으로', '~할 때', '설치하지 않으면', '맡은 사람이 없다', '지금'으로 쓴다. `기존으로`처럼 조사가 바로 붙어도 같다. `검토 시`, `배포 시`처럼 명사 뒤의 `시`는 동사로 푼다. `3시`, `시간`, `다시`, `표시`는 시각이나 다른 말이라 그대로 둔다.

고치기 전:
> 미설치 또는 비활성화 환경에서는 기존 어휘 검색과 FTS5 검색이 그대로 동작합니다.

고친 뒤:
> semantic extra를 설치하지 않았거나 꺼 두면 지금처럼 어휘 검색과 FTS5 검색을 씁니다.

고치기 전:
> 향후 코드 병합 시 점수 변화를 직전 결과와 비교할 수 있도록 기준 벤치마크를 먼저 마련합니다.

고친 뒤:
> 앞으로 코드를 병합할 때마다 점수가 직전 결과보다 나아졌는지 보려고 기준 벤치마크부터 만듭니다.

고치기 전:
> 기존으로 동작합니다.

고친 뒤:
> 지금처럼 동작합니다.

고치기 전:
> 검토 시 기준선을 봅니다.

고친 뒤:
> 검토할 때 기준선을 봅니다.

## 패턴 6. 스스로 매기는 평가 (self-rating)

맡는 이유나 결과를 쓰면서 '명확한 작업', '완결할 수 있는', '바로 마무리해'처럼 스스로 점수를 매기는 말이다. 독자가 확인할 수 없는 판단이라 근거가 되지 못한다. 평가어를 지우고, 그렇게 판단한 사실(사용자 결정이 필요 없다, 코드만 바꾸면 된다)을 쓴다. `불명확한`처럼 대상이 흐리다고 말하는 것은 스스로 매긴 평가가 아니다.

고치기 전:
> 코드베이스 안에서 완결할 수 있는 명확한 작업이며, 방금 병합된 하이브리드 검색 기능의 재현율과 지연 시간을 수치로 검증할 수 있습니다.

고친 뒤:
> 코드만 바꾸면 끝나는 일입니다. 방금 병합된 하이브리드 검색의 재현율과 지연 시간을 수치로 잽니다.

고치기 전:
> 사용자 결정이나 외부 응답을 기다릴 필요가 없고, 워크트리에서 바로 마무리해 README의 Glama 점수를 높일 수 있습니다.

고친 뒤:
> 사용자 결정이나 외부 응답을 기다릴 필요가 없습니다. 워크트리에서 끝내고 README의 Glama 점수를 올립니다.

## 패턴 7. 결과 없이 끝났다고만 쓴 보고 (empty report)

'AOM-17은 끝났습니다', 'AOM-19 채점을 마쳤습니다'처럼 끝났다는 말만 있는 보고다. 채널과 리뷰 댓글을 읽는 사람은 무엇이 달라졌는지 다시 찾아야 한다. 끝났다는 말 뒤에 결과 한 문장을 붙인다. 붙일 결과는 같은 일의 완료 보고나 커밋에서 가져오고, 없던 내용을 만들지 않는다. 티켓 번호로 시작하지 않아도 같다. `리뷰를 마쳤습니다`, `방금 작업을 마쳤습니다`처럼 끝났다는 문장뿐이면 빈 보고다. `마쳤어요`, `완료되었습니다`, `마무리했습니다`도 같다. `감사합니다`나 `확인 부탁드립니다`를 덧붙여도 결과가 없으면 빈 보고다. 같은 글에 결과 문장이 있거나, 끝난다는 문장 안에 점수나 달라진 점이 있으면 빈 보고가 아니다.

고치기 전:
> AOM-17은 끝났습니다.

고친 뒤:
> AOM-17을 마쳤습니다. `run_benchmark.py --semantic`으로 하이브리드 검색을 재 보니 recall@3이 0.40에서 0.84로 올랐습니다.

고치기 전:
> AOM-19 채점을 마쳤습니다.

고친 뒤:
> AOM-19 채점을 마쳤습니다. AOM-5는 68점, AOM-17은 86점이고, 후속으로 AOM-23과 AOM-24를 만들었습니다.

고치기 전:
> 방금 작업을 마쳤습니다.

고친 뒤:
> 방금 작업을 마쳤습니다. 벤치마크 4개가 통과합니다.

고치기 전:
> 리뷰를 마쳤습니다.

고친 뒤:
> 리뷰를 마쳤습니다. #28은 병합해도 됩니다.

## 함께 지킬 것

- 가운뎃점(·)으로 명사를 묶지 않는다. '구현·검증·병합'은 '구현하고 검증해 병합'으로 쓴다.
- '구축', '수행', '연동', '등록되었고' 같은 명사형 동사보다 '만들다', '하다', '잇다', '올라왔다'를 쓴다.
- 고칠 때 없던 판단이나 수치를 더하지 않는다. 원문에 없는 내용이 필요하면 고치지 말고 원문 작성자에게 묻는다.

## 완료 보고 전 점검

완료 보고(mission_finish의 summary와 next, 이슈를 review로 넘길 때 남기는 댓글, 채널에 올리는 결과 메시지)를 올리기 전에 초안을 이 순서로 점검한다.

1. 초안을 파일로 저장하고 `python3 scripts/lint_report.py 초안.txt`를 돌린다. 파일 없이 `echo "초안" | python3 scripts/lint_report.py`도 된다.
2. 찾은 줄마다 붙은 패턴 번호의 절을 읽고 고친 뒤 예처럼 고친다. 스크립트가 못 잡는 표현도 아래 목록으로 한 번 더 본다.
3. 상태 0(`ok: no polish patterns found`)이 나올 때까지 1과 2를 되풀이한다.
4. 고치기 전과 뒤의 수치, 파일 이름, 티켓 번호, 명령이 같은지 대조한 뒤 올린다.

세 도구는 훅이 대신 점검한다. `.claude/settings.json`에 건 `scripts/polish_hook.py`가 mission_finish의 summary와 next, issue_update의 comment, message_post의 text에서 패턴을 찾으면 호출을 막고, 찾은 줄과 그 패턴의 고친 예를 보여 준다. 예처럼 문장만 고쳐 다시 부른다.

스크립트는 패턴을 찾을 뿐 고치지 않는다. 일부러 남긴 표현이라 판단하면 그대로 올려도 되지만, 그 줄이 왜 괜찮은지 스스로 설명할 수 있어야 한다.

점검 목록:

- [ ] 번역투: '부합합니다', '~을 대상으로', '수행', '~하도록 구현했습니다', '이를 통해', '해당'이 없다. (패턴 1)
- [ ] 나열: 첫 문장이 사용자가 얻는 동작이고, 한 문장에 괄호 속 파일 이름이나 수치를 몰아 넣지 않았다. 괄호 없이 파일 경로 셋과 수치를 넣은 문장도 없다. (패턴 2)
- [ ] 언어: 채널이 한국어면 문장이 한국어다. 식별자, 명령, 지표 이름만 원문으로 둔다. (패턴 3)
- [ ] 긴 문장: '~한 상태에서', '~되었고', '~한 반면'으로 사실 서너 개를 잇지 않았다. `되어 있고`는 그대로 둔다. (패턴 4)
- [ ] 한자어 명사: '향후', '~ 시', '미설치', '비활성화', '기존'을 동사로 풀었다. '시간'과 '3시'는 그대로 둔다. (패턴 5)
- [ ] 평가어: '명확한', '완결할 수 있는'을 지우고 근거 사실을 썼다. '불명확한'은 그대로 둔다. (패턴 6)
- [ ] 빈 보고: 끝났다는 말 뒤에 결과 한 문장이 있다. 인사나 부탁은 결과가 아니다. (패턴 7)
- [ ] 가운뎃점과 명사형 동사('구축', '연동')를 쓰지 않았다. (함께 지킬 것)
- [ ] 수치, 이름, 번호가 고치기 전과 같고, 없던 판단을 더하지 않았다.
